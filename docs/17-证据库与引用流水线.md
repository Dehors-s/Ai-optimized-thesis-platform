# 17 证据库与引用流水线（v0）

> 回应两条提议：① 证据要有地方放，生成对应章节时模型必须看；② 引用要真实，
> 来源可追溯，检索工具拿不到的（知网等）走人工粘贴。
>
> 两条都对。但各缺一样东西：① 缺「强制」，光"让它看"不算约束；② 缺「分级」，
> "别人引过"只能证明它可能存在，不能证明它支持这句话。

---

## 0 先修正两个说法

**"让模型查看材料"不是约束。** 模型可以看了不用、用了不看、看了挑一半。
约束必须落在产物上：每个断言句带证据编号，检查器核对编号是否存在、是否属于本节、
是否被允许使用。看没看无法验证，标没标可以。

**"别人文章引了它"不是真实性证明。** 它只能当候选来源。文献表会传播错误：
原作者写错卷期、年份漂移、把会议名写成期刊名，下游照抄。我们自己的 v3 就是例子——
19 条里 1 条在 Crossref 只能弱匹配，还有几条题名与检索结果有出入。所以：
**候选可以来自别人的文献表，判定必须回到一手来源。**

## 1 三张表，一个 ID 空间

```
C-0001 主张（paper_ir.json）────┐
                                ├──► 正文句子
E-0001 证据（evidence.jsonl）───┤
R-0001 文献（refs.jsonl）───────┘
```

- `C-` 主张：一句话，可证伪，带强度与边界。
- `E-` 证据：数字、表、图、引文、数据、代码、负结果。**引用也是一种证据**（`type=citation`），
  所以"这句话背后有没有东西"只需要查一个库。
- `R-` 文献：真实的、可解析的作品记录。

统一 ID 的好处：正文里 `[E-0007]` 和 `[12]` 都能被同一套检查器追到源头；
导出时把 marker 剥掉即可。

## 2 证据库 `E-`

`evidence/evidence.jsonl`，一行一条：

```json
{
  "id": "E-0007",
  "type": "number",
  "claim": "训练/测试空间重叠使宏平均 F1 虚高",
  "value": "0.6584",
  "unit": "macro-F1",
  "source": {
    "kind": "experiment",
    "ref": "run-20261011-a",
    "locator": "metrics.csv:row=12",
    "url": "",
    "hash": "sha256:..."
  },
  "validity": {"n": 5, "seeds": [1,2,3,4,5], "ci": [0.6512, 0.6650], "split": "clean"},
  "strength": "moderate",
  "status": "verified",
  "notes": "与 0.6570 的差为 0.0014，低于噪声下限 0.002，不构成优势"
}
```

**来源四类**（`source.kind`）：

| 类型 | 含义 | 谁负责 |
|---|---|---|
| `experiment` | 跑出来的，有 run id / 脚本 / 日志 | 作者 |
| `file` | 用户给的数据文件、表格、PDF | 用户 |
| `url` | 检索到的网页或接口返回 | 系统 |
| `user` | 用户口头/文字断言，没有工件 | 用户 |

**状态三档**（`status`）：

- `verified`：有工件，能复现或能打开；
- `user_asserted`：用户说的，没有工件。**可以写进稿子，但必须降级表述，且检查器会提示；**
- `disputed`：两个来源冲突，禁止直接使用，必须作者裁决。

**负证据是一等公民。** 没起作用的模块、失败的种子、无效的对照，都要进库
（`type=negative`）。否则模型只会挑支持自己的数字，讨论节的"局限"就永远是空话。

**不可变。** 每个证据带 `hash`，改动产生新版本（`E-0007@v2`），正文记录用了哪版。
不这样做，证据悄悄变了，稿子还在引旧值。

**冲突显式化。** 两条证据冲突时都保留，各自标 `disputed` + `conflicts_with`。
禁止模型自己挑一个。这和 `innovation.md` 的"作者决定"是同一个机制。

## 3 章节绑定：从"看材料"到"证据包"

生成第 6 节时，不要给整库，给一个**证据包**：

```
本节主张：C-03（后处理带来 +0.0060 宏平均 F1）
允许证据：E-0007、E-0008、E-0011、E-0014（负）
禁止：E-0001（数据检查）、E-0002（预处理）
必须用到：E-0007、E-0011
```

配置写在 `project.json`：

```json
"evidence": {
  "allowed":  {"6 实验与结果": ["E-0007", "E-0008", "E-0011", "E-0014"]},
  "required": {"6 实验与结果": ["E-0007", "E-0011"]},
  "min_units": {"3 数据预处理": 3}
}
```

正文写法：

> 后处理在干净划分上带来 0.0060 的宏平均 F1 提升[E-0007]，但同一改动在重叠划分上
> 只有 0.0012[E-0008]，低于噪声下限[E-0011]。

**检查规则**（`tools/evidence_store.py check`）：

| 规则 | 判定 |
|---|---|
| 正文出现不存在的 `E-` 编号 | 失败 |
| 用了本节 `allowed` 之外的证据 | 失败 |
| `required` 没被用到 | 失败 |
| 本节证据数 < `min_units` | 失败 |
| 用了 `disputed` 证据 | 失败 |
| 用了 `user_asserted` 证据 | 提示 |
| 有证据从未被任何节使用 | 提示 |
| 证据 ID 重复 | 失败 |

**素材不足就不写。** 一节连 `min_units` 都凑不齐，正确行为是输出待办清单
（"缺：后处理在重叠划分上的对照"），而不是生成一段没有落点的话。
这是"素材少时加载通用模板"在**节**级别的对应物。

## 4 文献库 `R-`

`refs/refs.jsonl`：

```json
{
  "id": "R-0012",
  "key": "lipton2018label",
  "title": "Detecting and Correcting for Label Shift with Black Box Predictors",
  "authors": ["Lipton Z C", "Wang Y", "Smola A"],
  "year": 2018,
  "venue": "ICML",
  "type": "conference",
  "doi": "",
  "arxiv": "",
  "url": "https://proceedings.mlr.press/v80/lipton18a.html",
  "status": "verified",
  "provenance": {
    "discovered_via": "bibliography of R-0003",
    "query": "label shift black box predictors",
    "verified_by": "openalex",
    "verified_at": "2026-11-09"
  },
  "supports": [
    {"claim": "C-02", "span": "we show that ...", "intent": "method_origin"}
  ]
}
```

### 4.1 三段式：发现 → 核验 → 支撑

| 阶段 | 做什么 | 失败时 |
|---|---|---|
| 发现 | 从检索式、综述、近邻论文的文献表拿候选 | 候选进 `refs/candidates.jsonl`，不进正文 |
| 核验 | DOI / arXiv 解析；Crossref / OpenAlex 题名+作者比对；撤回检查 | 标 `weak` / `retracted`，不进正文 |
| 支撑 | 从原文取一句能支持该句的 span，标引用意图 | 没有 span 的，标 `unsupported`，只能当背景引用 |

**大部分工具只做第二步。** 第二步保证"这篇论文存在"，第三步才保证"这句话有依据"。
我们的 `ref_audit` 做第二步；第三步要读原文，见 4.3。

### 4.2 引用槽位

按章节角色固定槽位，槽位不满不写。以工程/实证类为例：

| 章节 | 槽位 | 数量 |
|---|---|---|
| 引言 | 领域背景、已有路线、最近的同类工作、本文与之的差别 | 4—8 |
| 方法 | 每个借用组件的出处（用了谁的损失、谁的骨干、谁的校准） | 每组件 1 |
| 实验 | 数据集出处、指标定义出处、基线实现出处 | 3—6 |
| 讨论 | 对照解释、替代解释、失效条件 | 2—4 |
| 结论 | 一般不需要新引用 | 0 |

槽位的作用是防"凑引用"。**一篇 19 条文献、每条只被引一次的稿子，是典型信号**：
说明引用是按位置填的，不是按论证需要引的。

### 4.3 引用意图

每条引用必须标一个意图：

- `background` 背景
- `support` 支持本文做法
- `contrast` 与本文不同/相反
- `method_origin` 方法来源
- `data_source` 数据来源
- `limitation` 局限/反例

检查器至少能查两件事：`contrast` 的句子必须出现对比词；`method_origin` 的组件必须
在 `method_map` 里能找到实现。这比"引用是否真实"更进一步，能挡住"真论文、假支撑"。

## 5 中文源与知网：把反爬变成流程

知网、万方、维普都有反爬和登录限制。**不要绕**，绕了是合规风险，也不稳定。
正确做法是把"人工复制"设计成一等路径：

```
系统生成待补清单（检索式 + 期望题名/作者/年份 + 槽位）
        ↓
用户在知网检索，点"导出/参考文献"，复制 GB/T 7714 文本
        ↓
粘贴进 refs/inbox.txt
        ↓
py tools/ref_store.py import-gbt --dir projects/x --file refs/inbox.txt
        ↓
解析成 R- 记录，status=manual，provenance.verified_by=user_cnki
```

`manual` 与 `verified` 的区别要保留：前者是"用户保证见过原文"，后者是"机器解析成功"。
两者都可以进正文，但报告里分开统计。**不能把 manual 写成 verified。**

中文期刊还应加两条约束：

- 中文文献比例下限（比如 ≥30%，按目标期刊定）；
- 近五年比例下限；这两条 `ref_audit` 已经在报，接进 `ref_store check` 即可。

## 6 命令与门禁

```bash
# 证据
py tools/evidence_store.py init  --dir projects/x
py tools/evidence_store.py add   --dir projects/x --type number --value 0.6584 \
    --unit macro-F1 --claim "重叠导致虚高" --source-kind experiment --source-ref run-a
py tools/evidence_store.py check --dir projects/x
py tools/evidence_store.py list  --dir projects/x

# 数字：facts.md 迁移 + 反查
py tools/facts_migrate.py --dir projects/x --dry-run
py tools/facts_migrate.py --dir projects/x
py tools/number_check.py  --dir projects/x

# 文献
py tools/ref_store.py init       --dir projects/x
py tools/ref_store.py import-gbt --dir projects/x --file refs/inbox.txt
py tools/ref_store.py import-bib --dir projects/x --file refs/library.bib
py tools/ref_store.py import-ris --dir projects/x --file refs/library.ris
py tools/ref_store.py check      --dir projects/x
py tools/ref_store.py export     --dir projects/x --apply   # 按首次出现重编号

# 支撑句
py tools/ref_support.py add  --dir projects/x --ref R-0001 --claim "C-02" \
    --intent support --show
py tools/ref_support.py scan --dir projects/x --ref R-0001

# 原有
py tools/ref_audit.py --text outputs/xxx.md --online
py tools/paperkit.py check --dir projects/x
```

门禁顺序：`facts_migrate` → `evidence_store check` → `ref_store check` →
`ref_support`（补齐支撑）→ `ref_audit --online` → `ref_store export --apply` → `check_project`。
前两步保证"有东西且对得上"，第三步保证"文献是真的、槽位够"，第四步保证"引用站得住"，
第五步保证"编号按首次出现"，最后一步保证"语体与规则"。

## 7 补充的坑

1. **引用级联。** 从别人文献表拿候选，会继承别人的错误和偏好（高引老文、小圈子）。
   对策：候选必须回到一手来源核验；统计 `discovered_via` 的分布，避免单一来源垄断。
2. **检索页面提示注入。** 抓回来的网页/PDF 里可能夹带"忽略以上指令"。
   证据入库时只保留结构化字段（题名、作者、年份、摘要、支撑句），不要把整页原文喂给生成模型。
3. **撤回与关注声明。** 引用前查 `is_retracted`；已经引用的，投稿前再查一次。
4. **数据与代码也要引用。** 数据集（Zenodo/Figshare DOI）、软件（JOSS/GitHub release）
   在方法节应有出处，很多期刊已经强制。
5. **时效。** 每条 `last_verified` 设 180 天过期，投稿前重验；文献会改版、会撤稿。
6. **同质化。** 槽位表不能做成填空模板，否则每篇论文的引用结构一模一样。
   槽位是"必须有"，不是"只能有"。
7. **规模。** 人工粘贴适合 10—30 条，不适合 200 条综述。综述类要单独设计
   （检索式 + 批量导入 + 抽样核验），不要硬套。
8. **版权与 ToS。** 批量抓取文献表、批量下载 PDF 可能违反平台条款；能用 API 就用 API，
   不能用就走人工。

| P2 | 综述类的抽样核验流程 | 待做 |

已知边界：

- `import-gbt` 只认 GB/T 7714 的文本格式，不认 NoteExpress / EndNote 的标签格式；
- `ref_support` 拿不到全文时只能基于摘要，摘要没说的事它证明不了；
- 重编号会改动正文与文献表，执行前先备份（`--apply` 会直接覆盖 `manuscript.md`）。

一句话：**证据库解决"有没有"，文献库解决"真不真"，槽位与意图解决"该不该引"。**
三件事分开做，才不会互相糊弄。
