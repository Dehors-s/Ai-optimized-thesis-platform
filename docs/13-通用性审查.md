# 13 · 通用性审查：四方向是「一个项目的分解」，不是产品模板

> 触发：四方向（样本分析、预处理、异构骨干、后处理）是这一个项目的贡献分解，不能当所有论文的骨架。
> 结论：产品要通用，必须把「论证模型」「章节角色」「贡献分解」「规则」四件事分开；四方向只是其中一种分解示例。

---

## 1 审查：哪些地方把项目概念写死了

| 位置 | 写死的东西 | 问题 |
|---|---|---|
| `paperkit/templates/outline.md` | 第 3/4/5 章固定为预处理/骨干/后处理 | 换成方法论文、综述、系统论文都不适用 |
| `paperkit/templates/manuscript.md` | 同样的固定章节 | 同上 |
| `tools/check_project.py` | 用 `## 3`、`## 5`、`## 6` 定位章节 | 章节编号一变就失效 |
| `tools/check_project.py` | 默认画像 `rs_method/rs_results/rs_discussion` | 只适用于遥感工程论文 |
| `tools/check_project.py` | 红线写死「0.6584 / 合作方 / 标签迁移 / 配额」 | 只适用于这一个项目 |
| `paperkit/templates/facts.md` | 「四个方向」表 | 事实清单应通用 |
| `docs/09` 四方向重排 | 把四方向当成方法主线 | 是本文的分解，不是通用方法 |

---

## 2 通用的四层模型

### 2.1 论证模型（不变）

```
Thesis → Claims → Evidence → Sections → Paragraphs
```

任何论文都一样：一个中心主张、若干子主张、每条子主张绑定证据、章节兑现主张、段落承担一步。

### 2.2 章节角色（按论文类型选）

| 角色 | 说明 | 是否必需 |
|---|---|---|
| `abstract` | 摘要 | 必需 |
| `intro` | 引言 | 必需 |
| `related` | 相关工作 | 视类型 |
| `problem` | 问题、数据与评测 | 实证/系统必需 |
| `method` | 方法（可多章） | 必需 |
| `results` | 实验与结果 | 实证/系统必需 |
| `discussion` | 讨论、局限 | 建议 |
| `conclusion` | 结论 | 必需 |
| `appendix` | 附录 | 可选 |

### 2.3 贡献分解（项目的，不是模板的）

四方向是「按误差位置分解」的一种。通用容器是：

```json
"decomposition": {
  "name": "按误差位置分解",
  "items": ["数据检查", "数据预处理", "异构骨干", "训练后处理"]
}
```

其他常见分解：

| 分解方式 | 例子 |
|---|---|
| 按流水线阶段 | 数据 → 表示 → 模型 → 解码 → 后处理 |
| 按方法组件 | 编码器、融合模块、损失函数、推理策略 |
| 按研究问题 | 问题一、问题二、问题三 |
| 按对比维度 | 精度、效率、鲁棒性、可解释性 |
| 按误差来源 | 输入、表示、输出（本项目） |

产品只要求「分解有名字、各项有证据」，不规定分几项、叫什么。

### 2.4 规则（每个项目配置，不写死）

```json
"rules": {
  "forbidden_phrases": ["优于", "高于对照", "纯自研", "证明了"],
  "required_attribution": {"number": "0.6584", "keyword": "合作方"},
  "required_statements": [
    {"if": "标签迁移", "then": "干净划分"},
    {"if": "配额", "then": "前作"}
  ]
}
```

## 3. 配置驱动的项目结构

`project.json` 成为唯一入口：

```json
{
  "name": "双高遥感论文",
  "paper_type": "engineering",
  "language": "zh",
  "journal": "测绘学报",
  "profiles": {
    "abstract": "rs_abstract",
    "method": "rs_method",
    "results": "rs_results",
    "discussion": "rs_discussion"
  },
  "sections": [
    {"title": "摘要", "role": "abstract"},
    {"title": "1 引言", "role": "intro"},
    {"title": "2 数据检查", "role": "problem"},
    {"title": "3 数据预处理", "role": "method", "profile": "rs_method"},
    {"title": "4 异构骨干", "role": "method", "profile": "rs_method"},
    {"title": "5 训练后处理", "role": "method", "profile": "rs_method"},
    {"title": "6 实验与结果", "role": "results", "profile": "rs_results"},
    {"title": "7 讨论", "role": "discussion", "profile": "rs_discussion"},
    {"title": "8 结论", "role": "conclusion"}
  ],
  "decomposition": {"name": "按误差位置分解", "items": ["数据检查", "数据预处理", "异构骨干", "训练后处理"]},
  "rules": {}
}
```

检查器只做三件事：

1. 按 `sections` 的标题切分正文（不依赖章节编号）；
2. 按 `role` 选画像（`profile` 可覆盖）；
3. 按 `rules` 跑红线，不再写死项目数字。

---

## 4. 论文类型模板

模板不再是「一份 outline」，而是「按类型选角色序列」：

| 类型 | 角色序列 |
|---|---|
| `empirical` | abstract → intro → related → problem → method → results → discussion → conclusion |
| `engineering` | abstract → intro → problem → method（多章，按分解）→ results → discussion → conclusion |
| `systems` | abstract → intro → related → design → implementation → evaluation → discussion → conclusion |
| `survey` | abstract → intro → taxonomy → comparison → challenges → conclusion |
| `theory` | abstract → intro → related → formulation → analysis → results → conclusion |

四方向模板归入 `engineering` 类型的一个示例，不再做默认。

---

## 5. 迁移动作

1. `paperkit/templates/project.json`：新增配置模板。
2. `paperkit/templates/types/{empirical,engineering,survey}/`：每类一份 outline 与 manuscript 骨架。
3. `new_project.py` 增加 `--type`，复制对应类型文件，并写 `project.json`。
4. `check_project.py` 改为读 `project.json`：按 `sections` 切分、按 `profile` 打分、按 `rules` 检查。
5. 现有四方向项目保留为 `engineering` 示例，不改内容。

---

## 6. 一句话

**通用产品提供「论证模型 + 章节角色 + 配置化规则」，项目提供「贡献分解 + 事实 + 证据」。四方向是后者的一个实例，不能当前者。**
